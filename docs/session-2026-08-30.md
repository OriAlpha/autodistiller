## 2. DFlash speculative decoding

New module `candidates/speculative.py`. Speculation is a **candidate dimension**, not
a compression method: it does not touch the target's weights, verification guarantees
the target's output distribution (so quality retention is 1.0 by construction), and the
cost/benefit lands on VRAM and throughput — axes the benchmark already reports.

```bash
autodistiller optimize --model Qwen/Qwen3-4B --max-vram 7GiB \
  --speculative <draft-repo> --launch-preset wsl-vllm
```

Every recipe is enumerated twice, with and without the draft, so the search answers
*does speculation help here* rather than assuming it does.

- `--speculative-tokens` defaults to the checkpoint's block size minus one (block 16 →
  15, block 8 → 7; both published families follow it).
- Draft weights are counted in the memory estimate. A DFlash draft for a 27B target is
  4.1B params — 7.71 GiB at bf16, more than the whole card.
- Drafts are **named, never derived**. They are published across `z-lab`, `incoai`,
  `RedHatAI` and community orgs with `-DFlash`/`-DFlash2` suffixes, each trained for one
  target. A guessed repo id is a plausible string that 404s mid-search.
- vLLM only. `Backend.supports_speculative` is False for llama.cpp; a speculative
  candidate there is rejected with a reason.

### Five defects found by actually running it

Each was found only by running the tool against real hardware, not by tests.

| # | Defect | Symptom |
|---|---|---|
| 1 | `_trim` grouped by method alone | Speculative candidates share a method with their plain twin and sort after it, so all 36 were dropped at the 12-candidate cap before anything ran |
| 2 | No draft-token budget in the launch | vLLM refused to start: `max_num_scheduled_tokens is set to -1536`, which is `512 - (15+1)*128` under its defaults |
| 3 | `--gpu-memory-utilization` hardcoded 0.85, then naively derived | Pinned, every candidate measured ~7.9 GiB regardless of size; derived from total, it exceeded free VRAM and the server refused |
| 4 | Launch flags absent from `benchmark_key` | Cache returned measurements taken against a differently configured server, reading as a hit |
| 5 | No validation of draft checkpoints | Failed minutes in, after compress and eval, with an error naming a config field but not the checkpoint |

## 3. Hardware and environment facts

Expensive to rediscover. All measured on this machine.

- **Card:** RTX 5070 Laptop, 7.96 GiB total, **6.83 GiB free once vLLM has started**.
  The Windows display driver holds some; vLLM's own CUDA context takes ~0.88 GiB more.
  `CUDA_CONTEXT_RESERVE_BYTES = 1 GiB` in `cli.py` is calibrated from this.
- **vLLM 0.27.1 in WSL supports DFlash** — `dflash` is in `SpeculativeConfig`, though
  `vllm serve --help` does not list `--speculative-config`.
- **vLLM cannot serve activation-quantized formats here.** `fp8-static` and `int8`
  (W8A8) both fail to start. `fp8` (dynamic), `int8-weight-only` and `int4-awq`
  (weight-only) serve fine.
- **`--max-vram 8GB` is too aggressive** — that is 7.45 GiB, 93.6% of the card, and the
  server refuses. Use `7GiB`.
- **JSON in a WSL launch must have escaped quotes.** Tested through the real
  `cmd.exe → wsl → bash` chain: unescaped, bash strips them and vLLM receives
  `{method: dflash}`. `LaunchSpec.nested_shell` handles it.
- **`_last_words(lines=12)` is too short for vLLM.** Its root cause appears *above* a
  long traceback, so the captured tail shows only stack frames. Not fixed.

## Resuming

**The open question: does int4 + DFlash fit, and is it faster?** Nothing has measured
it. Projection only — estimate plus the overshoot observed on one measured candidate —
put `int4-awq + dflash15` at ~7.5 GiB, which would fit with ~0.5 GiB spare. Treat that
as a guess.

```bash
uv run autodistiller optimize --model Qwen/Qwen3-4B --max-vram 7GiB \
  --speculative SubSir/Qwen3-4B-DFlash-b16-nvfp4 \
  --calibration wikitext2 --launch-preset wsl-vllm \
  --no-stop-early --method int4-awq --method fp8
```

Why each flag: `--no-stop-early` or the search stops at the first qualifying candidate
and never reaches the speculative ones. `--calibration` or AWQ/GPTQ fail at compression.
Two `--method` flags cut it to 4 candidates — the ones vLLM can actually serve, each
with and without the draft. Stale benchmarks no longer key-match (defect 4 above), so
this measures fresh while still reusing compression.

**Watch for:** whether `int4-awq-ctx2048-dflash15` gets past vLLM's config validation.
That is the fix under test.

**Caveat that is not fixed:** peak VRAM will not distinguish candidates. vLLM
pre-allocates its KV pool to the utilization target regardless of model size, so every
candidate lands near the budget. What separates them is whether the server starts and
what throughput it reaches — not peak VRAM. The VRAM constraint check is close to
meaningless under vLLM and deserves rethinking.

### Deferred

Marked in code with `ponytail:` comments (`grep -rn "ponytail:" src/`):

- `shape.py` — models alternating dense/MoE on a period are counted as fully sparse.
- `speculative.py` — draft size counts every declared parameter including embeddings.
  A draft conditioning on target hidden states may share the target's table; on a 248k
  vocab that is 2.5 GiB of the total. Over-counts deliberately. Narrow once a measured
  peak exists.
- `benchmark.py` — one prompt per run, which keeps TTFT comparable. A representative
  set would measure acceptance better but makes prompt length vary within a phase.
- `cli.py` — `CUDA_CONTEXT_RESERVE_BYTES` is one measured constant, not a probe.

Not addressed:

- `rtx-5070` profile is the 8 GiB Laptop card; the desktop 5070 is 12 GiB.
- `pareto.SIZE` axis is defined, exported, and never used in any frontier.
- `_percentile` uses `int(f*n)` where nearest-rank is `ceil(f*n)-1` — biased one rank
  high, same bias on every candidate, so ranking is unaffected.
- `experiment_key` fix (#9) left `benchmark_key` alone; launch flags were added to it
  later, so old benchmark entries no longer match. Intended.
